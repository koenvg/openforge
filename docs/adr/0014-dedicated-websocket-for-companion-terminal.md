# Use a dedicated WebSocket for Companion terminal attachments

Each Companion Terminal Attachment uses one authenticated WebSocket carrying terminal output, input, resize messages, attachment state, and exit signals. Binary frames carry UTF-8-encoded terminal output from the desktop and UTF-8-encoded terminal input from the phone; direction distinguishes their meaning, while JSON text frames carry attach, resize, ready, error, and exit control messages. Malformed UTF-8 is a protocol error rather than lossy output. After authenticated upgrade on the Task-scoped route, the client first sends an attach control message containing its columns and rows; the gateway resolves and resizes the running Agent PTY, sends replay, and then sends ready. Input remains disabled until ready. Before delivery, the gateway replaces unsupported iTerm2 inline-image sequences with a small text marker so image payloads never cross to the phone. The ready message identifies the initial-state strategy as `replay`; a later protocol may add `snapshot` without changing what an attachment means. The existing HTTP resources and Server-Sent Events stream remain responsible for snapshots and coarse attention/Task invalidations. A dedicated bidirectional channel preserves input/output ordering and low-latency interaction without either splitting writes across HTTP requests or generalizing the Companion event stream into a broad command socket. A slow attachment is closed and recovers through a fresh bounded replay; the gateway never blocks the desktop terminal session or silently drops output for a connected emulator.
